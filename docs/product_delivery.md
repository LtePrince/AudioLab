# 快速成谱交付与协作记录

更新：2026-10-17。本文件由产品设计 agent 维护；产品需求与指标以 [README](../README.md) 的确认状态为准。用户已授权产品设计与产品开发两个 agent 持续协作，更新后的授权允许实现，不再受此前仅讨论的阶段限制。候选质量、速度与玩家指标仍未自动获批。

## 当前交付边界

先完成可以实际运行和检查的闭环：**本地音频 → 选择定轨／无轨 → 生成整曲 → 音频同步视觉预览 → 导出谱面及诊断报告**。这是一项范围有限的工程里程碑，不代表整个产品、声学质量或真实可玩性已经验收。

- 定轨：固定四位置，保留 Tap / Drag / Hold / Flick；单独检查、报告和导出。
- 无轨：先交付静态单判定线 free-x，同样保留四键型和多指样本；动态判定线与演出模型保持后续独立里程碑，不以静态预览替代。
- 优先复用现有模型权重。首轮显示“基线谱”，不提供没有训练／评估证据的难度档位。
- 首轮提供本地命令入口与独立预览文件，不引入云服务、账户、付费、部署或大规模训练。后续逐步降低使用门槛。
- 预览用于检查音频、落点、键型、时长和整曲呈现，不具有真实播放器的输入判定与手感验收含义。
- 暂定 WAV／OGG 为已有实测格式；其他格式逐项实测后扩展。当前分析模块的 600 秒上限是实现边界，不能替代全链路实际支持范围测量。
- **BPM 暂需显式提供。** 现有 AR 生成受节拍时基影响；未实现 BPM 推断，不能把固定 120 标成估计结果。报告记录 `timing_source=provided`。这是基线限制，后续必须解决上传音乐后自动成谱的使用门槛。

## 独立审查口径

交付先提供固定提交、复现命令、逐曲结果和已知限制，再审查行为。所有检查记录“通过／缺陷／待证据”，不把“尚未验证”改写成通过，也不把尚待产品选择的部分判为代码缺陷。

当前工程审查逐项证据见 [产品审查记录](product_review.json)。固定 `f9c49c9` 已修复“候选全部覆盖但末和弦仍因 token 预算被截断”的完成状态缺陷，产品测试 11 项与后加尾部量化 1 项经独立分批复验。对照发现布局分块显著改变键型与布局分布，`cdb881c` 已恢复历史整曲布局默认并增加资源预检，分块布局只作显式实验，不允许资源不足时静默切换。

最终默认三曲长 102.77／144.13／178.81 秒，两模式合计耗时 31.79／38.05／62.22 秒，累计峰值 RSS 2.135 GiB、PyTorch GPU reserved 峰值 0.168 GiB；这些是三个开发样例上的运行测量，不是 P50/P95 或性能承诺。六份谱的硬检查和全部产物哈希经主会话独立核对。Firefox 已检查合成四键型／offset、旧快照三首整曲，以及新默认首曲两模式的真实 Hold 中段跳转与导出一致性。集成 `88750c8` 的全套测试由主会话独立复验为 221 passed，记录于 `develop` 的[集成说明](https://github.com/LtePrince/AudioLab/blob/2cea4f6/docs/product_integration.md)。工程里程碑可关闭，继续 N1；声学质量、音乐性、手感与动态演出保持未验收。

### N1：自动时间处理与可操作入口

该阶段紧接工程闭环，目的为让普通用户选音频和玩法后即可生成候选，BPM 手动填写成为可选覆盖。采用本地交互入口是当前可逆的工程默认，不代表已确定云部署。先完成受支持的稳定节奏输入；对不稳定、稀疏或不可估计输入明确说明状态，不伪造节拍置信度。

**时间表示与音乐结论必须分开。** 导出／AR 使用的 BPM 是时基参数，音乐速度估计是有来源、有误差的推断。两者各自记录；原始 Phigros JSON 的 BPM 也可能只是编码时基，未经听音审核不能当成音乐速度真值。候选事件继续以音频绝对秒保存，不把所有落点硬吸附到估计拍点。时基变化导致的 tick 四舍五入与事件合并必须可诊断。

首个低资源基线可复用已安装的 librosa 0.11.0：起音强度包络、周期相关速度估计和动态规划拍点。官方接口支持预先计算的包络；无起音强度时可返回 0 BPM 与空拍点，不能将其改写为检测到 120 BPM。[beat_track 官方文档](https://librosa.org/doc/0.11.0/generated/librosa.beat.beat_track.html)。局部速度可作为“不适合单一全局速度”的诊断；输出局部估计不等于已实现可靠 tempo map 或变速导出。[tempo 官方文档](https://librosa.org/doc/0.11.0/generated/librosa.feature.tempo.html)。这是显式算法基线建议，不宣称学习式 beat／downbeat 模型已完成。

| 编号 | 验收项 | 具体证据 |
| --- | --- | --- |
| N1a | 不手填 BPM 即可提交 | 本地入口选择音频、4K／free-x／两者，直接生成；真实支持曲完整跑通。模型路径、阈值与采样策略保留启动配置或开发设置 |
| N1b | 自动估计可追溯 | 记录估计方法、版本、输入哈希、分析范围、所选速度、半速／倍速等候选与选择依据；相关强度等启发分数不能标成已校准概率 |
| N1c | 不确定与失败可区分 | 至少区分自动估计、人工覆盖、节奏不稳／歧义、不可估计；不可估计不能静默填 120。可返回需要补充速度的信息；若允许未确认候选，预览与报告均明确该状态 |
| N1d | 人工覆盖不破坏时间 | 有限正数覆盖参数生效、来源明确；音频绝对事件时间仍正确；tick 量化偏移／事件合并有报告；非法输入不留下完成标记 |
| N1e | 时间算法的可控样例 | 已知速度点击、前导静音、弱起、半／倍速歧义、两段变速、稀疏事件与全静音。误差按分析帧与已知夹具时间检查；这些测试容差不是用户体验指标 |
| N1f | 两种布局的自动／手动对照 | 同曲同权重同 seed 比较人工时基与自动时基，分别记录时间量化、音符／键型／Hold、位置与修复变化。至少三首真实完整曲；没有真实音乐 BPM 标签时不报告速度准确率 |
| N1g | 本地交互可用 | 选择文件、启动、进度、取消、失败原因、重试、预览和导出在浏览器实际操作；一次只运行允许的作业数；失败／取消不会显示成谱完成 |
| N1h | 资源与声明一致 | 复用现有解码和特征，控制缓存／上传大小／运行队列；记录新增分析耗时与峰值。原有四键型、多指与无配额约束保持；未实现的难度和动态演出不做可用承诺 |

全局速度与局部 tempo map 是否都需实现，先看速度变化和下游对照证据。单一时基仍可表达绝对音频时间，无法因此推断模型已理解变速；若模型动作分布在半／倍速或变速音乐上明显退化，再推进时间表示与训练改动，不用默认常数掩盖缺口。节奏估计状态和方法先版本化，正式音乐质量门槛待标注与试测后确认。

现有 300 份谱面编码时基的只读清点范围为 104–540 BPM，120 仅 7 份，180 为 28 份；这只是训练／开发数据的表示分布，**不是音乐速度真值**。直接把自动算法偏好的半速估计交给 AR 可能改变布局分布，需要 N1f 对照。若后续拟合编码时基先验，只使用训练划分，不把全量清点或开发验证曲用于拟合。报告位于本地 `out/product_coordination/chart_timebase_inventory.json`。

## 可以自主决定与需要用户把关的事项

可以自主推进：本地单用户串行基线、复用现有权重、独立预览与 JSON 导出、资源保护、正确失败语义、工作区和分支拆分、可逆的 CLI／文件布局、测试与修复。阶段实现不代表候选模型或数值永久成为默认。

需要用户决定、但目前不阻塞工程闭环：最终目标播放器和设备／输入语义；动态演出是否作为首版发布必选；正式支持音乐范围；质量与等待时间承诺；所需玩家试玩组织。若待决事项阻塞下一阶段，先提交可审查的选项及影响，而不是把所有待定项同时抛回用户。

无法靠两个 agent 自动补齐的证据：独立的人类声学标注／复核、玩家完整试玩与主观体验认可。可以准备工具、样本和量表并继续其他工作，不能伪造这些结果，也不能宣称产品已完成。

## 协作协议与恢复入口

- 主会话：整合用户决定、资源调度、最终交付和跨分支集成。
- `/root/product_design`：维护 README 与本交付／验收记录；只读实现；独立复现缺陷；向开发 agent 发编号、严重性、证据和再验收条件。
- `/root/product_development`：隔离工作区完成实现、验证与推送；逐项响应；提交下一批可审查交付，不并行改产品文档。
- 两个 agent 通过协作消息直接沟通；提交、任务、证据仍写入文档，避免上下文压缩后丢失。消息传递只在本次活动会话中有效，不承诺结束会话后自动醒来工作。
- 循环：需求／验收 → 固定范围实现 → 交付证据 → 独立审查 → 修复并复验 → 标记该项通过 → 推进下一项。遇到实质产品取舍交主会话，不重复索要已有授权。
- 每次恢复先读 README、本文件、`docs/implementation_review.json`、开发交付报告及 Git 状态。尚未通过的工程、模型质量和人类验收分别保留，不因压缩或分支推送而自动关闭。
